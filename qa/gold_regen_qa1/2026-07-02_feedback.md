## Report-level defects

1. **D−1 High and Close are wrong, and everything derived from them inherits the error.** §6 states 01
   Jul High = $4,009.95 and Close = $3,989.09. The leak-free level file gives `prev_high_full =
   4115.53` (Δ $105.58 = 0.945×ATR14, far beyond the 0.20×ATR14 ≈ $22.33 failure threshold for a
   high/low) and `prev_close_full = 4031.08` (Δ $41.99 = 0.376×ATR14, far beyond the 0.115×ATR14 ≈
   $11.5 failure threshold for a close). Open ($4,006.20 vs $4,012.31, Δ$6.11) and Low ($3,960.25 vs
   $3,960.17, Δ$0.08) are both within tolerance, so the error is specific to the session's upper
   extent and closing print, not the whole row. A compliant §6 row for 01 Jul must show Close within
   $4,031.08 ± $4.47 (0.04×ATR14) and High within $4,115.53 ± $9.00 (0.09×ATR14) to be labelled
   "Corrob." — this row does not meet that bar and should not have been marked "Corrob. (Δ<$6)".

2. **RSI2 for 01 Jul does not match the market, even though it reproduces from the report's own
   (wrong) closes.** Report RSI2 = 0.0. Level file `rsi2_full = 72.0994`, `rsi2_cash = 100.0` — both
   more than 15 points away (Δ72.1 / Δ100), the Category 3 failure threshold. This is not an
   arithmetic-transparency failure (the report's own five closes do produce RSI2 = 0.0 given two
   consecutive down days), it is a direct consequence of defect #1: the underlying close series feeding
   RSI2 is wrong. Fix the OHLC series first; RSI2 will follow once the closes are corrected.

3. **Daily pivots are all wrong by the same amount as defect #1, because they are computed from the
   same bad H/L/C.** Report daily P = $3,986.43 vs level-file `d_full_P = 4035.5933` (Δ$49.16, fail).
   The pivot arithmetic itself is correct (P/R1–R3/S1–S3 all reproduce exactly from the report's own
   stated H/L/C — this is not a formula error), so once defect #1 is fixed, recompute the whole daily
   pivot table from `prev_high_full=4115.53`, `prev_low_full=3960.17`, `prev_close_full=4031.08`:
   compliant P = (4115.53+3960.17+4031.08)/3 = **4035.5933**, R1 = 2P−L = **4111.0167**, S1 = 2P−H =
   **3955.6567**, R2 = P+(H−L) = **4190.9533**, S2 = P−(H−L) = **3880.2333**.
   By contrast, the weekly pivots (P $4,089.82 vs $4,086.99, Δ$2.83; R1 Δ$5.41; S1 Δ$5.46) and monthly
   pivots (P $4,165.54 vs $4,165.5133, Δ$0.03; R1 Δ$1.10; S1 Δ$0.52) are accurate or near-exact — the
   error is isolated to the current session, not a systemic sourcing failure across all timeframes.

4. **ATR(14) is never stated as a number anywhere in the report**, despite the checklist (3.3)
   requiring it and it being used implicitly to size stops/caps. Add an explicit ATR14 figure to §9 (or
   §6). For reference, the level file's `atr14_full = 111.6736` (`atr14_cash = 85.5136`) — use

5. **Tick size and tick name are never declared in §2**, although §21 strategy cards are produced (M1
   Variables requires `[TICK_SIZE]`/`[TICK_NAME]` whenever `[PRODUCE_STRATEGY_RECOMMENDATIONS] = YES`).
   Add a Tick size / Tick name row to §2's Market Definition table (e.g., $0.01 / "tick", consistent
   with the $0.01-per-tick basis already used for Trade 2's stop distance).

6. **The daily-open anchor override is not logged as a compliant non-conformance.** §2 and §20 both
   state the anchor was "overridden to 00:00 UK for this run per instruction" without ever naming the
   populated instance's original anchor value that is being deviated from. The module's own rule is
   that a deviation "is a logged non-conformance, not an anchor" and must be recorded with the original
   value stated, the same converted time appearing on the card, in the handoff record, and in the
   report body — and must never be presented as if it were simply the operative anchor for the run. As
   written, a reader cannot tell what value this "override" is a departure from. Restate this as: "Anchor
   non-conformance: populated value = <X>; this run used 00:00 UK instead," with the same 00:00 UK time
   (converted) then carried onto every trade card that depends on the daily-open anchor.

## Card-specific defects

7. **Trade 2 — its construction contradicts its own declared regime.** The card is titled
   "regime-aware, TRANSITION → sell rally into resistance" and is built as a sell **limit** at daily R1
   ($4,012.61) — a RANGE-style fade (M5: "RANGE → limit at S1/S1.5/S2 (long) or R1/R1.5/R2 (short)").
   The M5 rule for a TRANSITION regime is explicit: Trade 2 must be **breakout side only**. A compliant
   Trade 2 under a TRANSITION call must instead be a stop-entry beyond a defined range boundary in the
   confirmed-break direction, not a resting limit order fading into resistance. Rebuild Trade 2 as a
   breakout-side card or relabel the regime.

8. **Trade 2 — the tick count on the entry cell does not reconcile with the tick basis used elsewhere
   on the same card.** The entry cell reads "$4,012.61 (daily R1) — 26,261 ticks level." The card's own
   stop distance ($52.39 = 5,239 ticks) fixes 1 tick = $0.01. On that basis $4,012.61 is 401,261 ticks,
   not 26,261. Correct the tick figure to 401,261 ticks, or state the alternative reference point the
   26,261 figure is actually measured from.

9. **Trade 3A — R does not match the card's own stated entry and stop.** The card states entry =
   $3,982.00, stop = $4,010.00, and R = $66.00 "from the trigger" (the $3,944.00 breakout-continuation
   level named in the entry cell). But $4,010.00 − $3,982.00 = **$28.00**, not $66.00. Per the static
   integrity rule, R must equal |entry − stop|. Recompute R from the stated entry/stop as $28.00 (2,800
   ticks at $0.01/tick), and re-derive TP1/TP2/TP3 distances from that corrected R rather than from the
   $3,944 trigger price, or restate the entry as $3,944.00 if that is the price actually meant to be
   traded.

10. **Trade 1 — correctly handled, no action needed.** The card is suppressed with an explicit
    SUPPRESSED row (composite score −0.2, |0.20| below the 0.25 conviction threshold) rather than
    omitted, which is the compliant behaviour under M5. No defect recorded here.
