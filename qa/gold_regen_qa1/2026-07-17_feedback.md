## Report-level defects

1. **Restriction breach — futures used as a primary consensus input, not corroboration-only.**
   §5: "The exchange-settled futures read and the real-time interbank read carry full weight," and §5
   states the final 3,995.50 figure is "the centre of gravity of the two highest-tier reads" — one of
   which is the CME-futures-derived 3,998.85. The brief's restriction requires spot gold consensus to
   treat futures as corroboration only, normalised, not as one of the primary weighted inputs. Rule:
   REVIEWER_BRIEF §2 row 1.1 / row 5.4 ("futures corroboration-only"). Fix: rebuild §5's weighting so the
   consensus price is set from spot-only reads, with the futures print retained only as a corroborating
   check on the range.

2. **D−1 close fails external reconciliation.** Report's 16-Jul close is 3,990.00 (used identically in
   §1, §3, §4, §6, §21b Trade 1 MARKET entry). Level file `prev_close_full = 3976.47` (diff 13.53) and
   `prev_close_cash = 3979.94` (diff 10.06). Tolerance for a close is ≤0.115×ATR14 before it is a
   Category 3 failure; 0.115×`atr14_full`(98.645) = 11.34. Both diffs exceed the tolerance for their
   respective basis (11.34 full / 8.85 cash) — this is not a basis-mismatch artefact, it fails either
   way. A compliant close must be 3,976.47 ± 4 (`_full`, ≤0.04×ATR) or flagged single-source if it can't
   be tightened to that.

3. **RSI2 fails external reconciliation (data problem, not an arithmetic one).** Report states RSI(2) =
   26.7 for 16 Jul. This *does* reproduce correctly from the report's own five stated closes (RS =
   12.80/35.19 = 0.3637 → 100−100/1.3637 = 26.7 — verified, no arithmetic fault). But it fails against
   the leak-free series: `rsi2_full = 8.2057` (diff 18.5, > 15-point failure threshold) and
   `rsi2_cash = 1.608` (diff 25.1). The defect is upstream, in the OHLC inputs (item 2 and item 4), not
   in the RSI2 formula itself. A compliant RSI2 computed from the file's true closes must land within 5
   points of 8.21 (`_full` basis).

4. **ATR14 understated by ~37%.** Report states ATR(14) = 62.50, self-disclosed as an estimate "from the
   corroborated 30-day range and observed daily true ranges rather than computed from a full
   fourteen-session validated series" (§19). Level file `atr14_full = 98.645`: relative diff 36.7% (>
   25% failure threshold; even against `atr14_cash` = 76.98 it is 18.8%, in the discrepancy band). Every
   downstream 0.25×ATR stop buffer (Trade 1: 15.63; Trade 2: 15.63; Trade 3A: 15.63) is therefore too
   tight by roughly 9 points (0.25×98.645 = 24.66 is the compliant buffer). Rule: brief §4 tolerance
   table, ATR14 row.

5. **Daily pivots — partial failure.** Report's daily pivots derive correctly from its own (wrong) H/L/C
   (verified: P/R1/S1/R2/S2/R3/S3 all reproduce exactly from H 4,065.39 / L 3,973.96 / C 3,990.00). Against
   `d_full` (P 4003.7567, R1 4038.2133, S1 3942.0133, R2 4099.9567, S2 3907.5567, R3 4134.4133, S3
   3845.8133): **S1 fails** (report 3,954.18 vs 3,942.01, diff 12.17 > 11.34) and **S3 fails** (report
   3,862.75 vs 3,845.81, diff 16.94 > 11.34); P (diff 6.02), R1 (diff 7.40) and S2 (diff 10.79) land in
   the discrepancy band; R2 (diff 1.25) and R3 (diff 2.63) are consistent. A compliant daily pivot table
   must be recomputed from `prev_high_full`/`prev_low_full`/`prev_close_full` (4065.5 / 3969.3 / 3976.47),
   which is exactly what the level file's `d_full_*` fields already give.

6. **Entire weekly pivot table fails.** Report's weekly pivots (from claimed week H 4,185.60 / L 4,038.60
   / C 4,062.40) reproduce correctly from those inputs, but every level fails against `w_full` (period

7. **Entire monthly pivot table fails beyond P — root cause identified.** Report's monthly pivots derive
   from claimed June H 4,382.85 / L 3,944.23 / C 4,189.50. Against `m_full` (period 2026-06): P is within
   tolerance (diff 6.68) but R1 (diff 12.21), R2 (diff 157.49), R3 (diff 151.96), S1 (diff 176.38), S2
   (diff 170.85) and S3 (diff 340.55) all fail, most catastrophically. Back-solving the level file's own
   pivot formulas shows the true June H/L/C behind `m_full_*` is H≈4,545.87 / L≈3,943.08 / C≈4,007.59.
   The report's L (3,944.23) and H (4,382.85) match the **25-session swing extremes**
   (`swing_low_25d_full`=3943.08, `swing_high_25d_full`=4382.22) almost exactly, not the true calendar-month

   an earlier-June high of ~4,545.87 that falls outside the 25-session lookback window but inside the
   calendar month. Rule: brief §4 (numbers reconcile against level file) / M1_Variables §B (monthly pivot
   period = prior calendar month, not a rolling 25-session window). Fix: source the true June 2026
   calendar-month H/L/C (reconstructable exactly as H 4,545.87 / L 3,943.08 / C 4,007.59 from `m_full_*`)

8. **§6's "corroborated / live" label for the daily H/L/C overstates confidence given the leak-free
   check.** §11 states "prior-session H/L/C dual-source corroborated… Levels are live, not indicative,"
   yet the close component of that same triplet fails reconciliation against the execution series by
   13.53 (item 2). Per the brief's pivot-corroboration guidance, "the level file *is* the execution
   series" — a live/corroborated label should not stand where the underlying close diverges beyond the
   failure threshold from that series. Downgrade the daily-pivot corroboration language accordingly, or
   re-source the close.

9. **Minor — TradingView citation is internally inconsistent.** §4's TradingView row is dated "16 Jul,
   close" but its own Notes call it an "earlier-session print… stale relative to NY afternoon." A row
   cannot simultaneously be a session close and a stale earlier print. Relabel the Date/Time column to
   the actual print time, not "close."

10. **Minor — the anchor-override note is self-contradictory as written.** §20: "The instance-configured
    anchor was overridden for this run… and set to 00:00 UK… It is worth noting that the override
    resolves to the same value the instance already carried, so no behavioural change results." An
    override to an unchanged value is not an override. Either state plainly that no override occurred
    (anchor = instance default, 00:00 UK), or, if a real departure did occur, name the value departed
    from. As written this cannot be distinguished from silently presenting a changed value as the
    anchor, which M1_Variables' `[DAILY_OPEN_ANCHOR]` rule requires to be avoided.
